# 客服回复幻觉检测

批量检测智能客服回复中的"幻觉"——编造的政策、错误的退货地址、杜撰的产品参数。

检测一律走 **规则前置 + 大模型断言级复核**，没有离线分支。

---

## 快速开始

```bash
./mvnw spring-boot:run
```

浏览器打开 <http://localhost:8080/>，填入回复数据与模型接口（地址 / 密钥 / 模型名），点检测。

**不需要预先配置任何东西**——密钥在页面上现填，随请求发给本机后端，由后端调用模型，
用完即弃。服务端不持有、不缓存任何凭据，所以配置文件里不会出现 API key。

> **本项目需要 Java 17。** 如果机器上默认的 `JAVA_HOME` 指向更早的版本，
> 命令行构建会在编译阶段失败（`release 17 not supported`）。此时显式指定：
>
> ```bash
> JAVA_HOME=/path/to/jdk-17 ./mvnw spring-boot:run
> ```
>
> 在 IntelliJ 里运行则不受影响——IDE 用自己的 SDK 配置，与系统 `JAVA_HOME` 无关。

## 检测页面

### 调用链

```
浏览器  ──POST /api/detect/batch──▶  本机后端  ──▶  大模型端点
        （数据 + 地址 + 密钥）              （规则 + 断言级核对）
```

请求模型的是后端，不是浏览器。这样安排有三个好处：

- **没有跨域问题**。浏览器只跟同源的本机后端打交道，不受同源策略约束。
  （浏览器直连模型时端点必须支持 CORS，而各家支持情况并不一致。）
- **密钥不落在浏览器**。后端按请求临时构造客户端，用完即弃，
  不落盘、不缓存、不记日志。
- **检测逻辑只有一份**。规则前置、断言拆分、聚合口径都在 Java 侧，
  不会出现"页面一套、服务端一套"然后两边结果对不上。

### 报表内容

| 章节 | 内容 |
|---|---|
| **一、幻觉分类定义** | 四类 + 严重度，附本次检出分布。定义从 `/api/taxonomy` 拉取，与 Java 枚举同源 |
| **二、检测方法** | 规则前置 + 断言级复核的流程、判定口径、失败处理 |
| **三、检出率** | 提供人工标注时给出准确率 / 精确率 / 召回率 / F1 与漏检、误报清单；未提供时说明为什么算不了 |
| **四、AI 工具使用情况** | 开发过程中 AI 承担了什么、核查出了哪些错误假设 |
| 附、逐条检测结果 | 每条的类型、严重度、判定理由与断言级证据链，可按状态筛选 |

### 参数校验

后端是权威校验方（页面上的校验只是让用户早点看到问题），错误**一次列全**，
不是遇到第一个就返回：

- **回复数据**：顶层非数组、空数组、元素不是对象、缺少 `id` / `system_reply`、
  重复 id（警告）、`knowledge_base` 为空（警告）
- **接口地址**：缺 `http://` 前缀、协议不是 http/https、公网明文 http（警告）、
  缺版本前缀会导致 404（警告）、已带 `/chat/completions` 会重复拼接（警告）
- **模型名 / 密钥**：非空校验；连本地模型时允许空密钥并给出说明
- **人工标注**：`is_hallucination` 必须是布尔值、必须带 `id`

失败时返回结构化 JSON 而不是 Java 堆栈：模型不可用是 `503 llm_unavailable`，
配置或数据有问题（含 JSON 语法错误）是 `400`。

**任何一条失败即中止整批**并拒绝出具汇总指标——不产出看起来正常、实际不可信的报告。

> **页面目前没有自动化测试**，改动后需要手工验证。
> 后端逻辑有 65 项 Java 断言守着（见[项目结构](#项目结构)）。

## 一、幻觉分类体系

### 分类轴的选择

按**出错对象**分四类，而不是按"与知识库的偏离方式"。

这个选择是推演之后改的。最初设计用的是"知识库有没有依据"这条轴：无据=凭空编造，
有据而冲突=事实偏离。但把它套回数据立刻塌了——20 条里绝大多数案例的知识库**恰好写了相反的值**
（h01 知识库写"7天无理由"回复说"30天"、h06 写"PU合成革"回复说"头层牛皮"……），
按那条轴分，10 条候选里 7 条要改判，剩下 3 条撑不起一个类别。

换成"出错对象"之后，分类直接对应**业务定责**——业务方拿到结论就知道该找谁处理：

| 类型 | 定义 | 业务归属 |
|---|---|---|
| **参数事实编造** | 产品参数、材质、成分、品牌关系等客观断言与知识库不符，或知识库中根本无据 | 商品 / 运营 |
| **政策规则编造** | 退货、发票、发货、支付、优惠、退货地址等业务规则与知识库不符，或知识库中根本无据 | 运营 / 客服 |
| **能力越界** | 声称执行或查询了系统并不具备的动作（知识库明示未接入该接口或不具备该功能） | 工程 |
| **信息遗漏误导** | 选择性遗漏知识库中的关键限定条件，把带条件的提示抹平成确定性结论，导致建议失真 | 客服 |

### 严重度：独立的横切轴

严重度不作为一个类型，而是横切维度——类型回答"错在哪"，严重度回答"有多严重"。

| 档位 | 判据 |
|---|---|
| **S1 高危** | 可能造成人身健康风险，或不可逆的资金与物流损失 |
| **S2 中** | 导致用户做出错误的购买或售后决策 |
| **S3 低** | 表述失准，对用户决策影响有限 |

**定级规则：类型给基线档次，关键词上调，只升不降。** 由 `TaxonomyRules` 实现。
不允许下调是刻意的——模型对严重度的判断不稳定，容易把高危案例说成"轻微"。
触发 S1 的关键词是健康风险（孕妇、医生）、材质欺诈（成分、牛皮、真皮）
与不可逆的物流操作（地址、仓库、寄到），词表在 `app.rules.severity-escalation-keywords`。

### 判定口径

这是整套体系里最关键、也最容易含糊的一条。它写死在提示词与规则里：

| 情形 | 判定 |
|---|---|
| 知识库明确支持 | **放行** |
| 知识库明确记载相反的值 | **幻觉**（CONTRADICTED） |
| 知识库保持沉默（含"未标注""未提及"），而回复给出**可核查的肯定断言** | **幻觉**（UNSUPPORTED） |
| 知识库未逐字覆盖，但回复**语义一致**且保留了对冲词 | **放行**（CONSISTENT_HEDGED） |
| 问候、致歉、共情等非事实性表述 | 不参与判定 |

第三条与第四条必须成对存在，否则会二选一地翻车：

- 只有第三条 → **h16 被误报**。知识库只说"图片可能存在轻微色差"，没提"实物拍摄"，
  严格执行"没写就是幻觉"会把这条干净回复判错。
- 只有第四条 → **h09、h15 被放过**。知识库写着"未标注NFC功能""未提及其他品牌关联关系"，
  回复却肯定地说"支持NFC""是某品牌子品牌"——这是典型的编造，必须抓。

判据落在**回复有没有保留知识库里的限定条件**：

- 保留了（"基本""轻微""可能""建议咨询医生"）→ 放行
- 抹平成确定性结论并给出相反断言 → 幻觉

## 二、检测方法

### 架构：规则前置 + 大模型断言级复核

```
                     ┌─────────────────────────────┐
   ReplyRecord ─────▶│ 规则检测器（确定性、免调用）  │
                     └──────────────┬──────────────┘
                                    │ 未命中
                                    ▼
                     ┌─────────────────────────────┐
                     │ 拆分成 1~N 条独立断言        │
                     │ 逐条对知识库核对             │
                     │  SUPPORTED / CONTRADICTED /  │
                     │  UNSUPPORTED / CONSISTENT_   │
                     │  HEDGED / NON_FACTUAL        │
                     └──────────────┬──────────────┘
                                    ▼
                     ┌─────────────────────────────┐
                     │ 聚合 → 类型 + 严重度 + 证据链 │
                     └─────────────────────────────┘
```

**为什么拆到断言粒度。** 一条回复可能同时说对了 A、说错了 B。
整体判定容易被"大体正确"主导从而漏检，逐条核对则不会。

**为什么规则前置。** 有一类案例的知识库直接写着"未接入物流查询接口"，回复却说"我帮您查了一下"——
这种**动作声明与能力声明正面对撞**的信号，规则判定比模型更稳、更省。

### 规则检测器的关键设计：判极性，不判关键词

**这是规则路径最容易写错的地方。** 知识库写着"不支持货到付款"、回复也说
"不支持货到付款"时，关键词命中，但这是**正确**回复。

所以规则判的不是"回复里出现了 X 这个词"，而是：

> （回复声称执行了某个动作 **∨** 给出了可核查的肯定断言） **∧** 知识库声明该能力/该信息不存在

其中"知识库声明不存在"有三种形态，各有各的坑：

- `未接入` / `不具备` / `需转人工` —— 能力缺失，对应能力越界
- `未标注` / `未提及` —— 信息缺失，对应参数事实编造
- `无 X` —— 存在否定，需要**排除构词**：知识库里的"7天**无理由**退货"，
  这里的"无"是构词成分而不是"没有这项政策"，不排掉就会误判

### LLM 路径

提示词见 `Prompts.java`。判定口径、部分正确需要逐条拆、数值差异必须逐项比对，
全部写死在提示词里，**不留给模型自由发挥**——模型不被告知这套规则，
就会在两种相反的判法之间随机漂移。

工程细节：`temperature=0`；结构化输出解析失败时剥离 ```json 围栏后重试一次；
两次都失败则抛出异常。模型客户端 `OpenAiCompatibleChatModel` 直接说 OpenAI 协议，
按请求构造，地址与密钥用完即弃。

### 失败即中止，不静默降级

**这是整个工具最关键的一条安全约束。**

模型不可用（网络不通、401、限流、返回的 JSON 解析不了）时，整批立即中止，
而不是把那些案例判成"没有幻觉"。

为什么单独强调：如果按"没发现问题就是没问题"处理，你会得到一份**格式完整、
指标漂亮、但完全错误**的报告——而且没有任何迹象表明它错了。
对检测工具来说，静默的假阴性比崩溃危险得多。

```
HTTP 503
{
  "error": "llm_unavailable",
  "message": "模型调用失败，检测已中止——不会产出可能错误的结论。",
  "detail": "案例 case-2 的模型调用失败，已重试 2 次。检测结论不可信，
             因此中止运行，而不是把它当成「没有幻觉」。原因：401: ...",
  "hint": "检查本次使用的端点地址、密钥与模型名是否正确，以及网络是否可达。"
}
```

检测器内部不存在任何"降级成干净"的分支——`LlmDetectionException` 的类注释写明了原因，
`LlmClaimDetectorTest` 里有三条测试守着这一点（调用失败、输出无法解析、返回空数组）。

代价是：数据量大时跑到一半失败，前面的结果也拿不到。这是刻意的取舍。

### 并发

逐条串行太慢，后端用固定线程池并发调用模型（上限 4）。想让调用方自己调这个上限的话，
把它提到请求参数里即可。

## 三、检出率

### 本节数据待补

检测一律需要真实大模型，本项目**尚未在真实模型下跑过**，因此没有可复现的指标数字。
配置好模型后跑一次即可得到：

```bash
./mvnw spring-boot:run
# 打开 http://localhost:8080/，填入数据与标注，点检测
```

> **未测量的东西不宣称。** 早先的版本引用过一组数字，那来自一个已经移除的实现，
> 无法用当前代码复现，因此不再列出——留着一组跑不出来的数字，比没有数字更糟。

### 这个数据集的指标陷阱（与用什么方法无关）

无论用哪种检测方法，这批数据都有一个必须先说清楚的属性：

**20 条里 18 条是幻觉、2 条干净，正负比 9:1。**

这直接决定了"准确率"在这里是**失效指标**：

| 策略 | 准确率 | 召回率 | 实际价值 |
|---|---|---|---|
| 什么都不做，一律判幻觉 | **90%** | **100%** | **零** |
| 什么都不做，一律判干净 | 10% | 0% | 零 |

一个完全不做判断的策略能拿到 90% 准确率和 100% 召回率。所以本工具：

- **报表以漏检数与误报数为准**（这也正是任务要求的那两个量），准确率只作参考；
- 正例占比超过 80% 时，报表会显式给出分布提示，而不是让使用者对着一个数字下判断；
- 要有统计意义的结论，需要更大规模、正负更均衡的标注数据。

## 四、误判原因分析

### h04 为什么最容易漏检 —— 部分正确

> **知识库**：支持电子发票，下单后在订单详情页申请。**暂不支持纸质发票**。申请时需提供发票抬头和税号。
> **回复**：可以的，支持电子发票和纸质发票。下单时在备注里写上发票抬头和税号就行。

回复里有三个断言：「支持电子发票」对、「支持纸质发票」错、「在备注里填写抬头」错。

**对错混杂是这类案例最本质的困难。** 任何"整体印象式"的判定——无论是人扫一眼，
还是模型一次性读完整段——都容易被"大体正确"主导，从而放行。

还有一层更隐蔽的：知识库里**同时出现了**"电子发票"和"纸质发票"两个词，
差别只在紧随其后的是"支持"还是"暂不支持"。字面重合度极高，
因此**任何基于词汇相似度的方法在这条上必然失效**——它匹配得到词，匹配不到极性。

这条案例是断言拆分存在的理由，也是主检测器最可能漏的一条。
它能否被正确拆成两条分别判定，取决于模型而不是规则。

### h16 与 h20 —— 一对镜像

这两条形态几乎一样，都是"知识库给了一段带条件的提示，回复给了一个干脆的结论"，
但一个该放行、一个该判幻觉：

| | 知识库 | 回复 | 人工判定 |
|---|---|---|---|
| **h16** | 商品图片因拍摄光线、显示器色差等原因，**可能**与实物存在**轻微**色差，请以实物为准 | 图片都是实物拍摄的，颜色**基本准确**，不过不同手机屏幕**可能会有轻微色差** | ✅ 干净 |
| **h20** | 约 **30%** 用户反馈偏大半码，**建议脚瘦的用户选小半码** | 尺码标准，**不偏大也不偏小** | ❌ 幻觉 |

区别在于：

- h16 **保留**了知识库的限定条件（"基本准确"+"轻微色差"）→ 干净
- h20 **丢掉**了限定条件（"约 30% 偏大" → "不偏大"）→ 幻觉

检测器必须能区分「**降级表述**（保留了对冲词，放行）」和
「**抹平表述**（丢弃对冲并给出反向结论，判幻觉）」。这个切分已经显式写进提示词。

**这是需求阶段就定下的取舍**：保住 h16 不误报，优先于抓住 h20。
理由是数据集只有 2 条负样本，为 1 条真正例去冒 1 条假正例的险不划算。
代价是 h20 可能漏检——这条列在「已知边界」里，不藏着。

### 规则路径结构上处理不了的那批

规则判据只覆盖一类结构：**知识库明示"没有这个能力 / 没有这条信息"**。
对应另一类结构——「**知识库写了正确值、回复改成了别的值**」——规则完全无力。
对照数据集，这正好是下面这些：

| 案例 | 知识库写的 | 回复说的 |
|---|---|---|
| h01 | 7天无理由 | 30天无理由 |
| h02 | 蓝牙 5.0 | 蓝牙 5.3 |
| h04 | 暂不支持纸质发票 | 支持纸质发票 |
| h06 | PU合成革 | 头层牛皮 |
| h08 | 24小时发货 / 中通、韵达、圆通 | 48小时 / 顺丰 |
| h13 | 孕妇建议咨询医生 | 孕妇可以放心使用 |
| h17 | USB-A 输出 | Type-C 接口 |
| h20 | 约30%用户偏大半码 | 尺码标准，不偏大也不偏小 |

**规则路径的漏检集，就是 LLM 路径必须补上的那部分。**
这个差集直接回答了"为什么这个任务需要模型"——也正因为如此，
单纯把规则写得更复杂不是出路：要抓这些，本质上需要理解语义，而不是堆更多的关键词。

### 容易误判的 case 的共性

综合来看，容易出问题的是这几种：

1. **回复部分正确**（h04）—— 对错混杂，任何"整体印象式"的判定都会放行
2. **知识库与回复语义一致但措辞不重合**（h16）—— 词汇方法必错，需要语义理解
3. **极性差异**（h12 vs h19）—— h12 知识库说"不支持"回复也说"不支持"（正确），
   h19 知识库说"无此政策"回复说"有的"（幻觉）。**关键词完全相同，只有极性相反**
4. **数值细微差异**（h02 的 5.0 vs 5.3、h08 的 24 vs 48）—— 字符串高度相似，语义完全不同
5. **限定条件被抹平**（h20）—— 与第 2 类表面相似，但方向相反，需要区分

第 3 类和第 5 类是最难的：它们要求检测器理解"同一句话在不同上下文里含义相反"。

## 五、接口

只保留页面需要的两个。

| 接口 | 说明 |
|---|---|
| `GET /` | **检测页面**（静态资源，启动即可用） |
| `GET /api/taxonomy` | 分类体系定义，供页面渲染「幻觉分类定义」章节 |
| `POST /api/detect/batch` | **批量检测**：请求里带上数据与模型凭据，后端现构客户端去调用 |

## 六、配置与容器化

### 配置文件

`src/main/resources/application.yml` 里只有三样东西：

- **`app.rules.*`** —— 规则检测器的判据词表与正则
- **`spring.jackson.property-naming-strategy`** —— 接口统一 snake_case 输出
- **`spring.config.import`** —— 加载 `.env`

**没有模型凭据配置。** 地址、密钥、模型名由调用方在页面上现填，
所以不需要 `spring.ai.*` 那套"启动时定死一家厂商"的配置。

> **YAML 写法坑**：凡值里带冒号的（`${VAR:default}` 占位符）都加了引号。
> YAML 普通标量里冒号后跟空格会被解析成新的键值对。正则用单引号包裹，
> 因为 YAML 单引号内的反斜杠是字面量。
>
> **`.properties` 与 `.yml` 并存时 `.properties` 优先**，`.yml` 会被静默忽略，
> 配置"没生效"却找不到原因。本项目只保留 `.yml`。

### 规则词表可调

`app.rules.*` 下是**中文客服领域的话术特征**，不是某批数据的答案。
各家话术差别很大——有的平台说"未接入"，有的说"暂未开通"；有的把退货地址叫"寄回地址"。
按自己的知识库措辞调整即可，不用改代码重新发版。

### 接入任意 OpenAI 兼容端点

换厂商只改三个值，页面上直接填：

| 厂商 | base-url | 模型名示例 |
|---|---|---|
| OpenAI | `https://api.openai.com/v1` | `gpt-4o-mini` |
| DeepSeek | `https://api.deepseek.com/v1` | `deepseek-chat` |
| 通义千问 | `https://dashscope.aliyuncs.com/compatible-mode/v1` | `qwen-plus` |
| 智谱 GLM | `https://open.bigmodel.cn/api/paas/v4` | `glm-4-flash` |
| Kimi | `https://api.moonshot.cn/v1` | `moonshot-v1-8k` |
| 本地 Ollama | `http://localhost:11434/v1` | `qwen2.5:7b` |

**base-url 必须带上各家自己的路径后缀。** 程序把值原样使用，只在末尾拼
`/chat/completions`，**不会**替你补 `/v1`。写成 `https://api.openai.com` 会请求到
`https://api.openai.com/chat/completions`，直接 404。各家后缀并不统一——
智谱用的是 `/api/paas/v4` 而不是 `/v1`。

**本地模型不需要密钥**，留空即可（空 key 不发送 `Authorization` 头）。页面上的校验
会识别 `localhost` / `127.0.0.1` 并放行。

### `.env` 的格式硬约束

`.env` 会被两个解析器读取，写法必须落在交集之内：

1. Spring Boot —— 通过 `spring.config.import` 用 properties 解析器读
2. `docker run --env-file` / Compose 的 `env_file`

| 写法 | 后果 |
|---|---|
| `export KEY=value` | ❌ Spring Boot 会把 `export` **当成键名**；`docker run --env-file` 直接报错退出 |
| `KEY="value"` | ❌ Spring 与 Docker **都不剥离引号**，引号成为值的一部分 |
| `KEY=value # 注释` | ❌ 行尾注释会成为值的一部分 |
| `KEY=value` | ✅ 两者都认 |
| 整行 `# 注释` | ✅ 两者都认 |

本项目 `.env` 里只有 `SERVER_PORT` 一项——密钥在页面上现填，不该出现配置文件里。

### 容器化

```bash
# 构建（国内可加 MAVEN_MIRROR 加速）
docker build -t csr-hallucination-detection .

# 运行
docker run -p 8080:8080 csr-hallucination-detection

# 用 .env 注入配置（可选，不传也能起）
docker run -p 8080:8080 --env-file .env csr-hallucination-detection

# 或者用 compose
docker compose up
```

`.dockerignore` 排除了 `.env` 与 `target/`——密钥不会进镜像，
构建在容器内的多阶段流程里从源码完成。

## 七、AI 工具使用情况

本项目全程使用 **Claude Code** 辅助开发。下面记录的是实际发生的事。

### 需求阶段：逐项确认判定口径

动手前先做了一轮设计评审，逐个确定分类体系、判定口径、检测架构、模型接入方式、评测口径。
其中**分类轴被推翻重设计过一次**——最初按"知识库有无依据"分，套回数据发现多数案例的
知识库恰好写了相反的值，整个分类会塌；改成按"出错对象"分四类。

### 用 AI 做事实核查，纠正了多个错误假设

关键技术前提没有靠记忆下结论，而是逐个查证官方文档与 jar 包内的实际内容：

| 核查项 | 结果 |
|---|---|
| Spring AI 版本兼容性 | 确认只有 2.0.x 支持 Spring Boot 4.x；1.0 / 1.1 只支持 3.5.x |
| OpenAI 的 base-url 要不要带 `/v1` | **要带**。配置值原样传给 SDK，SDK 只拼 `/chat/completions` |
| api-key 留空会怎样 | **不会报错**。空值走无鉴权分支，意味着配错了要推迟到第一次调用才暴露 |
| 配置里中文能否作 map 的键 | **不能**。中文元素会被静默丢弃，抛出的却是"String 转 Map 失败"这种指错方向的错误 |

其中"base-url 要不要带 `/v1`"和"空 key 会怎样"两项，
**最初写进文档的说法都是错的**，是查了源码才纠正过来的。

### 实现阶段：先验证再断言

- **规则检测器先写测试再调优。** `RuleBasedDetectorTest` 把"知识库与回复同向否认时不得误报"
  这类不变式锁成断言，规则一改、破坏不变式就构建失败。
- **测试不依赖任何数据文件。** 全部用测试内构造的合成用例，词表也是测试自带的、
  与仓库示例数据无关的词汇。这样测试验证的是"引擎逻辑对不对"，
  而不是"某批数据的答案背得牢不牢"——换业务数据时测试不用跟着改。
- **模型不可用时的行为被测试守住。** 早先的实现里，模型调用失败会被 catch 掉、
  返回"判为干净"——模型一挂，整批数据全报干净，产出一份格式完整、指标漂亮、
  但完全错误的报告。这个静默故障比崩溃危险得多，现已改为失败即中止，
  并由 `LlmClaimDetectorTest` 里三条测试守住。
- **测试替身抓出了两个真 bug。** 用脚本化的 `StubChatModel` 驱动 LLM 路径做单元测试时，
  发现 `DetectionResult.clean()` 会把断言证据链整个丢掉（判为干净的案例看不到"查过哪些断言"），
  以及严重度升级词匹配的是整条回复而不是被判为幻觉的那条断言。
  **只有把模型调用换成可控替身、构造出特定输入才会暴露**——跑真实模型时它们被数据"掩护"住了。
- **端到端跑一遍抓到了单元测试看不见的 bug。** 当时用 Node 写了页面逻辑测试（53 项断言），
  又起了一个假的 OpenAI 兼容服务把整条链路跑通，才暴露出：`Metrics` 是 record，
  Jackson 只序列化**记录组件**（四个计数），而 `accuracy()` / `precision()` 这些是**方法**，
  压根不会进 JSON。Java 侧调用一直正常、单元测试全绿——但前端读 `metrics.accuracy`
  会拿到 `undefined`，指标卡显示成空白。**单靠单测永远发现不了，问题只存在于序列化边界上。**
  （那套页面测试后来按要求移除了，页面目前只有手工验证。）
- **重构后做了逐位回归。** 把配置项外置、测试换成合成用例之后，重新跑了一遍全量数据，
  各检测器的指标与重构前**逐位一致**。结构改变不应改变行为，这件事必须验证而不是假设。

## 八、已知边界与局限

诚实列出这套方案做不到的事：

1. **检出率尚未测量。** 检测需要真实大模型，本项目写作时尚未跑过，因此没有任何
   可复现的指标数字。**未测量的东西不宣称。**

2. **h20（信息遗漏）可能漏检。** 需求阶段就选定"保住 h16 不误报"优先于"抓住 h20"，
   数据集只有 2 条负样本，为 1 条真正例去冒 1 条假正例的险不划算。这是有意识的取舍。

3. **h04（部分正确）是最可能漏的一条。** 对错混杂的回复天然抵抗"整体印象式"判定。
   如果真实模型下 h04 仍被漏掉，说明断言拆分这条设计没有兑现，应当回头改主设计。

4. **规则判据需要按业务话术校准。** 词表已全部外置到 `application.yml` 的 `app.rules` 下，
   代码里不含任何领域词汇——但这不等于开箱即适用于所有业务。那套词是按中文电商客服的
   话术整理的，换成金融、医疗客服时仍需要按自己的知识库措辞调整。**不调就上，
   规则路径会大面积漏判。**

5. **失败即中止意味着一次失败会丢掉整批结果。** 这是刻意的权衡：静默降级会产出
   看起来正常、实际全错的报告，那比崩溃危险得多。但代价是 1000 条数据跑到第 999 条
   失败时，前 998 条的结果也拿不到。后续可以加断点续跑，目前没有做。

6. **检测结果不落盘。** 页面驱动的路径下，结果只存在于页面和浏览器的内存里，
   刷新即失。后端不保存任何检测记录——这是为了保护数据与凭据，但也意味着
   留档要靠浏览器打印 / 存为 PDF。

7. **页面没有自动化测试。** 改动页面后需要手工验证。

8. **20 条样本、18:2 的不平衡分布，任何指标都要谨慎解读。**
   要得到可信的结论，需要更大规模、正负更均衡的标注数据。
